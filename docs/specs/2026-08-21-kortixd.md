# kortixd — the Kortix compute node

Status: **PROPOSED**. Author: Marko + Claude. Date: 2026-08-21.
Supersedes the runtime half of `2026-08-20-convergent-runtime.md` (which stays
correct; this generalizes it). Reopens, under a different structure, the
architecture reverted on 2026-07-30 (`ffc5fb769e`).

---

## 1. Problem

`apps/kortix-sandbox-agent-server` is a supervisor welded to one deployment
shape. Three facts define the limit:

1. **It cannot be installed.** A box exists because the API called
   `provider.create()`. The daemon receives an identity it cannot request. There
   is no registration endpoint in the codebase.
2. **It cannot be reached except through a provider.** `resolveIngress()` is
   mandatory on `SandboxProvider`. `sandbox_provider` is a closed Postgres enum
   of `daytona | platinum | e2b`. A machine outside those three is not
   expressible.
3. **It supervises exactly one harness.** OpenCode REST is hardcoded through
   4,532 lines. Driving `claude` or `codex` requires replacing that path, which
   is what failed in July.

The consequence: a laptop, an EC2 instance, a k8s pod, or a customer's bare
metal cannot be Kortix compute.

### 1.1 What already exists and works

Do not rebuild these. Generalize them.

| Asset | Where | State |
| --- | --- | --- |
| Convergence + staged swap + immutable floor | `src/runtime-assets.ts`, `apps/sandbox/entrypoint.sh` | Shipped, dev-verified 2026-08-20 (#6673, #6676) |
| Enrollment, device-auth, OS service install, reverse relay | `packages/agent-tunnel`, `apps/api/src/tunnel` | Shipped. 6,021 + 3,702 lines |
| Host services: files, find, pty, port-proxy, web-proxy, static-web | `src/routes/*`, `src/static-web.ts` | Shipped, already deployment-agnostic |
| Multi-workload boot | `KORTIX_WORKLOAD` in `src/main.ts` | Shipped. Three modes, no seam between them |

### 1.2 What was tried and reverted

2026-07-08 decided ACP-first. PR #4510 built it (four harnesses, live matrix
12/12). 2026-07-30 removed it. The stated cause, from `8953c09b2c`:

> the refactor did not add a parallel ACP path, it rewrote shared REST code

Three regressions survived with the flag off. This spec treats that sentence as
the primary design constraint. See §12.

## 2. Decision

Build **`kortixd`**: one binary that turns any machine into a Kortix compute
node.

- Concept name: **Kortix compute node**. Binary: `kortixd`. Registry table:
  `kortix.compute_nodes`.
- A node **enrolls** with a Kortix API and holds an outbound channel to it.
- A node **hosts one session at a time and many over its life**.
- A node **drives real harness binaries** — `opencode`, `claude`, `codex` — as
  peer adapters behind one interface. It never embeds an agent SDK.
- The API stays the brain: auth, models, secrets, policy, session state,
  and the convergence manifest are centralized.
- **A node degrades to standalone.** An unreachable API must not stop a running
  session (§5.5).

---

## 3. Non-goals

- Concurrent sessions on one node. Decided: serial only (§8). Revisit after P2.
- Metering self-registered nodes. Deferred; `compute_nodes` is designed so
  metering is additive (§10.3).
- Replacing the OpenCode REST path. It becomes the first adapter and keeps
  its exact behavior (§12).
- ACP as the product↔daemon boundary. Out of scope. ACP may be how a specific
  adapter talks to a specific harness; it is not the node contract.
- A second language or toolchain. `kortixd` stays a single Bun-compiled binary.

---

## 4. Principles

**P1 — The node manages compute; the API owns the product.** kortixd knows
processes, workspaces, ports, health, and convergence. It does not know
triggers, channels, connectors, billing, or entitlements.

**P2 — The image is a cache; the API is the truth.** Unchanged from
`2026-08-20-convergent-runtime.md`. Extended: it now governs harness binaries
too, and a node reports what it already has rather than being forced to a
uniform image.

**P3 — Nothing is a special case.** A Daytona box, an EC2 instance, and a
laptop are the same object with different `provisioning` metadata. If a code
path branches on "is this a real sandbox", the abstraction has failed.

**P4 — Additive, never substitutive.** A new adapter is added beside existing
ones. No new capability may edit the code path of a shipped one. This is the
July lesson, stated as a rule (§12).

**P5 — Degrade, do not fail.** Every dependency on the API has a defined
behavior when the API is unreachable, and none of them is "stop the session".

**P6 — Fail toward the binary that worked.** Preserved verbatim from the
convergent-runtime design: immutable floor, independent re-verification,
crash-budget rollback.

## 5. Architecture

```
                    Kortix API — control plane (centralized)
                     · node registry, enrollment, assignment
                     · auth · models · secrets · policy · session state
                     · /v1/runtime-assets manifest = convergence truth
                              ▲
             outbound channel │ node dials out, holds it open
              (+ REST for bulk transfer)
                              ▼
┌──────────────────────── kortixd ────────────────────────────────────┐
│ NODE CORE                                                            │
│  identity + enrollment · convergence · local store · control server  │
│  process supervisor · capability report · health                     │
├──────────────────────────────────────────────────────────────────────┤
│ SESSION MANAGER          one active · many over the node's lifetime  │
│  claim → prepare workspace → run → release → clean                   │
├──────────────────────────────────────────────────────────────────────┤
│ WORKLOAD ADAPTERS                                                    │
│  session(harness) · monitor · warm-seed · app                        │
│    └ HARNESS ADAPTERS — real binaries                                │
│        opencode-rest (today, unchanged) · claude-code · codex        │
├──────────────────────────────────────────────────────────────────────┤
│ HOST SERVICES            unchanged, already portable                 │
│  files · find · pty · port-proxy · web-proxy · static-web · egress   │
└──────────────────────────────────────────────────────────────────────┘
```

### 5.1 Node core

Target under 800 lines. Owns:

- **Identity.** Node id, node token, API base URL. Persisted in the node store,
  never in 74 environment variables.
- **Enrollment.** `kortixd enroll` — device-code for a human, token for
  automation. Reuses `packages/agent-tunnel/src/agent/device-auth.ts`.
- **Convergence.** `src/runtime-assets.ts`, lifted intact, generalized from a
  fixed component list to the manifest's `components` map.
- **Control server.** The existing Hono app. Two listeners: the network port
  (today's 8000) and a Unix socket for local/standalone use.
- **Supervisor.** Process trees, restart budgets, health, graceful drain.
- **Capability report.** What this machine is and has (§7.2).

### 5.2 What the node core must not contain

`git.ts` (1,454 lines), `project-env.ts`, `secret-capabilities.ts`,
`egress-shim/*`, `llm-proxy.ts`, `opencode*.ts`, `monitor-runner.ts`. These
become adapter-owned or host services. The current `main.ts` (2,760 lines) is
dismantled into the core plus three workload adapters.

### 5.3 Configuration contract

`config.ts` declares 29 keys. A source scan finds **62 `KORTIX_*` names read
directly from the environment**, plus a handful reached indirectly through
constant indirection (`env[SECRET_CAPABILITIES_ENV_NAME]`). The contract is
roughly 70 names, and today no single place states it.

- Source order: node store file → environment → CLI flags. Later wins.
- Every key is declared, typed, documented, owned, and validated at boot.
- `kortixd doctor` prints resolved config, what is missing, and why it matters.
  A failing install must say so in one screen.
- Legacy `KORTIX_*` names keep working through a declared compatibility map for
  one release. The map is a table, not scattered reads.

**Tripwire:** a test scans the source for environment reads and fails when it
finds a name the contract does not declare. This is what keeps the contract
true after the refactor, not review discipline.

#### 5.3.1 Config is LIVE, not a boot snapshot

**This is the subtlest constraint in the whole daemon, and getting it backwards
would break warm-seed forks.**

`reloadSessionEnv()` (`main.ts:720`) writes `process.env[k]` at runtime from
`/etc/pt-env`. A warm-seed fork boots with the *deriving* session's credentials
and adopts the real session's identity afterwards. So:

- A direct `process.env.X` read is **correct after adoption** — it sees the new
  value.
- A `cfg` captured at boot is **stale after adoption**.

The existing code handles this by deriving `cfg2 = loadConfig()` on adoption and
threading it explicitly (`server.reload(cfg2)`, `materializeRepo(cfg2)`,
`startSessionRuntime(…, cfg2, …)`). `routes/health.ts` goes further and reads
`/etc/pt-env` directly, because even `process.env` is wrong pre-adoption.

Therefore the config contract must **not** be a frozen module-level object.
Each declared key carries a `reload` mode:

| `reload` | Meaning |
| --- | --- |
| `boot` | Fixed for the process. Ports, paths, state dirs. Safe to snapshot. |
| `session` | Re-read on every claim/adopt. Identity, tokens, repo, prompt, LLM. |

A `session` key read from a snapshot is a bug, and the contract makes that
checkable rather than a thing to remember. Related incident: 2026-06-10, forks
answering health on `main` with the deriving session's credentials.

### 5.4 Transport

Two paths, one contract:

| Path | When | Carries |
| --- | --- | --- |
| Provider ingress | Node has a reachable inbound address (today's cloud boxes) | Everything, unchanged |
| Outbound channel | Node has no inbound address (laptop, NAT, k8s without ingress) | Everything, multiplexed over the held connection |

The API picks per node from `compute_nodes.reachability`. Callers never branch.
The channel reuses `apps/api/src/tunnel/core/{rpc-core,cluster-forwarder}.ts` —
cross-instance forwarding is already solved there (401 lines).

### 5.5 Standalone behavior

"Works standalone somewhat" made concrete. For each API dependency, the defined
degraded behavior:

| Dependency | API unreachable |
| --- | --- |
| Convergence manifest | Skip this pass. Keep running binaries. Retry next hook. Already the shipped behavior. |
| Turn relays (`turn-stream`, `turn-question`) | Spool to the local store, replay on reconnect, bounded by size and age. Today they are dropped. |
| Audit relay | Already spools locally. Unchanged. |
| Git clone credential | Fail the clone with a named reason. A session cannot start without a repo. |
| Session assignment | No new sessions. **Running sessions continue.** |
| Secrets | Use the last delivered set. Do not clear. |
| Local control server | Fully functional over the Unix socket. `kortixd` CLI can start, inspect, and stop a local session with no cloud at all. |

The strong statement: **a running session survives an API outage.** A node that
loses its channel keeps working and reconciles when it returns.

## 6. The workload interface

One interface. Today's three modes and tomorrow's adapters implement it.

```ts
export interface Workload {
  readonly kind: 'session' | 'monitor' | 'warm-seed' | 'app'
  /** Validate the environment before anything is spawned. */
  preflight(ctx: NodeContext): Promise<PreflightResult>
  /** Bring the workload up. Must be idempotent. */
  start(ctx: NodeContext, assignment: Assignment): Promise<void>
  /** Liveness + readiness, folded into GET /kortix/health. */
  health(): WorkloadHealth
  /** Additional routes this workload owns, mounted under its own prefix. */
  routes?(): Hono
  /** True while work would be severed by a restart. Gates the agent swap. */
  busy(): boolean
  /** Graceful stop. Must leave the node reusable. */
  stop(reason: StopReason): Promise<void>
}
```

`busy()` is load-bearing: it is the existing agent-swap blocker
(`registerAgentSwapBlocker`) promoted to a first-class member, so a new workload
cannot forget to declare when a swap would sever work.

## 7. Harness adapters

### 7.1 The interface

A session workload delegates to a harness adapter. Adapters drive **real
binaries**. No SDK embedding — that was rejected on 2026-07-08 and stays
rejected.

```ts
export interface HarnessAdapter {
  readonly id: 'opencode' | 'claude-code' | 'codex'
  /** Is this harness usable on this machine, and at what version? */
  detect(): Promise<HarnessDetection>
  /** Spawn the real binary. Returns the local surface the node proxies. */
  spawn(ctx: SessionContext): Promise<HarnessProcess>
  /** How the node talks to it. Not a shared abstraction — per adapter. */
  transport: 'rest' | 'acp' | 'stdio'
  ...
}
```

`transport` is deliberately per-adapter. OpenCode keeps `rest` and its exact
current code path. Whether `claude-code` uses ACP or its own CLI protocol is
that adapter's private decision and changes nothing else.

### 7.2 Detection, not baking

July baked four adapters into every image and re-versioned every template. This
inverts it:

- At boot, `kortixd` detects which harnesses exist on the machine and at what
  version.
- It reports them as node capabilities.
- The API assigns work only to a node that advertises the required harness.
- Convergence may *install* a missing harness when policy allows it — the same
  mechanism that already installs `opencode` on mismatch.

A laptop with `claude` and `codex` already installed becomes useful with zero
image work. That is the whole point of the reframe.

### 7.3 Ordering

`opencode-rest` is the only adapter in P0–P2 and is byte-identical to today.
`claude-code` and `codex` land in P3, after the seam is proven in production by
a shipped adapter that nothing else can disturb.

## 7.4 `kortix node` — the CLI is the installer and the fleet manager

There is no separate installer. `apps/cli` already ships as a single compiled
binary, is distributed through GitHub releases, is baked into every image, and
converges itself against the API (`/v1/runtime-assets/cli`). It is the natural
place to install, enroll, inspect, and retire a node.

`kortix hosts` is a different concept and must not be conflated: it selects
*which Kortix instance* you authenticate against. `kortix node` operates *on
machines* belonging to the active host.

```
kortix node install [--version <v>] [--service]   fetch kortixd for this
                                                  platform, verify the digest,
                                                  install the OS service
kortix node enroll [--token <t>]                  device-code by default;
                                                  --token for automation
kortix node status                                this machine: enrolled?
                                                  claimed? converged? which
                                                  harnesses detected?
kortix node list                                  every node on this account,
                                                  with status and last heartbeat
kortix node logs [-f]                             tail the local daemon log
kortix node enable | disable                      accept or refuse new claims
                                                  without unenrolling
kortix node drain                                 finish the current session,
                                                  accept nothing new
kortix node restart | stop
kortix node uninstall                             remove the service, revoke the
                                                  node token, delete local state
```

Design rules:

- **`install` reuses convergence, not a new download path.** The daemon binary
  and its digest come from `/v1/runtime-assets/agent`, which already serves them
  and already verifies. One artifact path for install and for update.
- **`enroll` reuses `agent-tunnel`'s device-code flow** verbatim
  (`packages/agent-tunnel/src/agent/device-auth.ts`), including the credential
  file rules: regular file, owner-checked, mode `0600`.
- **`install --service` reuses `agent-tunnel`'s service drivers** — LaunchAgent
  on macOS, user systemd on Linux, Task Scheduler on Windows
  (`src/agent/service-drivers.ts`). That code is shipped and tested; a second
  implementation would be a regression.
- **`status` works with no network.** It reads the local node store over the
  Unix socket (§5.5). A node you cannot reach must still be able to tell you why.
- **`enable` / `disable` / `drain` are the operator's controls** on a machine
  Kortix does not own. Someone lending a laptop must be able to take it back
  mid-session without uninstalling anything. `drain` is the polite version;
  `disable` is immediate for new work.

This also collapses a duplication: `kortix node install` on a laptop and a
provider baking `kortixd` into an image become the same act, differing only in
who runs it.

## 8. Session lifecycle on a node

Decided: **one active session, many over the node's lifetime.**

```
enrolled/idle → claimed → preparing → ready → running → releasing → idle
```

- **claim** — the API assigns a session; the node accepts or refuses (busy,
  missing capability, draining).
- **prepare** — workspace materialization, secret delivery, harness spawn.
- **release** — harness stopped, ports freed, spooled relays flushed.
- **clean** — workspace removed. **Isolation between successive tenants on a
  machine Kortix does not own is a hard requirement, not a cleanup nicety.** The
  clean step is the first thing that must be adversarially tested (§13).

This breaks `session_id == sandbox_id`, which is load-bearing today. §10 covers
the data-model change. `sandbox_id` remains for provider boxes; it becomes a
property of a node, not the node's identity.

### 8.1 The claim transition already exists

**P1 is not new machinery.** `armSeedAdoption()` (`main.ts:394`) is already a
working `claim`, shipped and running in production on every Platinum warm fork:

```
adopt(trigger):
  reloadSessionEnv()                 // new identity arrives via /etc/pt-env
  cfg2 = loadConfig()                // re-derive — see §5.3.1
  server.reload(cfg2)                // re-arm the proxy with the new tokens
  configureGlobalGitIdentity(cfg2)   // re-key git
  materializeRepo(cfg2)              // prepare the workspace
  startSessionRuntime(cfg2)          // run
```

That is `claimed → preparing → ready → running` with the names removed. It is
triggered by `SIGHUP` or by `KORTIX_SESSION_ID` appearing in `/etc/pt-env`, and
it is guarded by a one-shot `adopted` latch.

The session manager generalizes this rather than inventing it:

- **claim** — generalize `adopt()`; the trigger becomes a channel message or a
  local control call, not only a file poll.
- **release** — does not exist yet. This is the genuinely new code.
- **clean** — does not exist yet, and is the risky half (§13).

Consequence for sequencing: P1 is smaller than it looks, and its real work is
`release` + `clean`, not `claim`. It also means the seam is validated by a path
already carrying production traffic.

## 9. Convergence, generalized

Unchanged in mechanism. Three extensions:

1. The manifest's `components` map governs harness binaries as well as
   `agent | cli | opencode | managed-skills`. Every v1 and v2 key stays
   permanent — deployed daemons read them, and a test guards it.
2. `policy` gains per-component install permission, so a laptop can be told
   "converge the daemon, never touch my `claude` install."
3. The staged-swap handshake (`agent.next` + `.sha256`, exit `75`, independent
   re-verify, `agent.pinned` latch) is preserved verbatim, including the
   root-owned immutable floor.

**The binary rename is a convergence event.** `kortix-agent` → `kortixd` must
not break a box mid-update. The supervisor learns both names; the floor keeps
its current path for one release; the manifest advertises both. Fully specified
before P0 lands.

## 10. Data model

### 10.1 `kortix.compute_nodes`

```
node_id            uuid pk
account_id         uuid
name               text
status             enum(enrolling, idle, claimed, running, draining, offline, retired)
reachability       enum(inbound, channel)      -- which transport §5.4 picks
provisioning       jsonb                        -- {kind:'provider'|'self', provider?, external_id?}
capabilities       jsonb                        -- arch, cores, memory, disk, harnesses[]
agent_build        bigint                       -- last converged manifest build
node_token_hash    varchar(128)
last_heartbeat_at  timestamptz
enrolled_at        timestamptz
```

`provisioning` is where a Daytona box and a laptop stop differing. This is P3
of the principle list made concrete: allocation becomes metadata, not identity.

### 10.2 Relationship to today's tables

- `session_sandboxes` keeps its shape; it gains `node_id`. A provider box gets
  a `compute_nodes` row on create, so there is exactly one registry from day
  one and no dual-write.
- `sandbox_provider` enum is **not** extended. Self-hosted nodes carry
  `provisioning.kind = 'self'` and no provider. No enum migration; no repeat of
  the 2026-07-10 prod enum drift.
- `tunnel_connections` is the model for the channel and is a candidate to merge
  into `compute_nodes` in P4, not before.

### 10.3 Metering

Deferred. `compute_nodes` carries no billing column. When the product answer
arrives, metering attaches to `sandbox_compute_sessions` by `node_id` and is
purely additive. Nothing in P0–P2 forecloses either answer.

## 11. Phases

Each phase ships to dev and is verified there before the next begins.

### P0 — Node core, no wire change
Extract the core. Declare the config contract. Introduce the workload
interface with today's three modes behind it. Rename to `kortixd` with a
convergence-safe path. **Zero observable behavior change.**

*Exit:* `pnpm test` green; a dev session boots, runs a turn, restarts, resumes,
and converges with byte-identical `/kortix/health` output; the swap handshake
test suite still 9/9; no bare `process.env` outside `config.ts`.

### P1 — Session manager
`compute_nodes` table and backfill. `claim/release/clean` lifecycle. A node
hosts a second session after the first ends. Cloud behavior unchanged.

*Exit:* one dev node proven to run session A, release, clean, and run session B
with no leakage of workspace, secrets, or process state between them.

### P2 — Enrollment + channel + `kortix node`
`kortix node install/enroll/status` (§7.4). Outbound channel. Standalone
degraded mode (§5.5). **A laptop runs a real Kortix session.**

*Exit:* `kortix node install && kortix node enroll` on a clean laptop with no
inbound address, then a full session driven from the web UI; `kortix node
status` correct with the network down; API killed mid-turn and the turn
completes; relays replay on reconnect.

### P3 — Harness adapters
`claude-code` and `codex` adapters on real binaries. Detection and capability
reporting. Manifest `runtime:` re-lands behind the adapter interface.

*Exit:* the same project runs a turn on all three harnesses; the OpenCode path
is provably untouched (§12).

### P4 — Consolidation
Fold the Go `appd` in as a workload adapter. Fold `agent-tunnel` in — a laptop
is a node. Remove `resolveIngress` from the data path where a channel exists.

## 12. What must not break — the July rule

The 2026-07-30 rollback happened because a second runtime rewrote shared code.
Three mechanical guards, all in P0:

1. **The OpenCode adapter is created by moving files, not editing them.**
   `opencode*.ts` moves under `workloads/session/harnesses/opencode/` with no
   content change in the same commit. The diff must be pure rename. Any
   behavior change is a separate, reviewed commit.
2. **A characterization suite is captured before the move.** Record today's
   `/kortix/health`, boot timeline, route table, and a full turn transcript from
   a real dev session. It becomes a golden test. P0 passes only if the output is
   identical.
3. **The interface is proven by two implementations before a third is designed.**
   `monitor` and `warm-seed` already exist and must fit the workload interface
   unchanged. If they need special-casing, the interface is wrong and P3 does
   not start.

Stated as a review gate: **no pull request in P0–P2 may modify a line inside
`opencode*.ts`.** If one appears to need it, the seam is in the wrong place.

## 13. Verification

Per `CLAUDE.md`: real inputs, real outputs, on every surface.

- **P0** — golden characterization diff; `apps/sandbox/scripts/test-entrypoint-swap.sh`
  9/9; a real dev sandbox reports the expected `runtime` block; `pnpm test`.
- **P1** — a scripted two-session run on one dev node, asserting the clean step
  with an adversarial probe: write a secret, a file, a running process, and a
  listening port in session A; assert none is observable in session B.
- **P2** — enrolled laptop driving `dev.kortix.com`, with the network partition
  test run live. Assert the outbound payload and the visible UI state, not just
  a screenshot.
- **P3** — one project, three harnesses, one turn each, transcripts captured.
  Plus a proof that the OpenCode path's golden output is still identical.

## 14. Risks

| Risk | Mitigation |
| --- | --- |
| A repeat of July: the seam leaks into the REST path | §12, enforced as a review gate on the diff |
| The fleet drain — the supervisor only reaches a box on re-provision | Land the rename in the same image bump as P0. Pay it once, as already budgeted |
| A laptop node leaks state between tenants | P1 exit criterion is an adversarial isolation probe, not a cleanup review |
| Enrollment token on a personal machine is a credential | Reuse agent-tunnel's rules: `0600`, owner-checked, rotatable, revocable. Node token is node-scoped, never account-scoped |
| Scope: this touches everything | Phases ship independently. P0 and P1 are invisible to users and can be merged without P2 ever landing |
